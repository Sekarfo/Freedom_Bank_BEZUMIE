# CQA — Conversation Quality Analytics

Прототип оценки качества диалогов операторов Freedom Broker (хакатон Freedom Broker × Data Challenge NU).

Система оценивает каждый диалог (чат или звонок, RU / KZ / EN) по настраиваемому чек-листу, доказывает каждый вывод номером реплики и дословной цитатой, считает итог кодом по правилам чек-листа и оставляет финальное слово за человеком через апелляции.

## Как это работает

```
Транскрипт → 1. Предобработка (код)     нумерация реплик, язык, подсказки-эвристики
           → 2. Модель-судья (1 вызов)  Claude Opus 5.5: по каждому критерию значение, номера реплик,
                                        дословная цитата, обоснование, уверенность
           → 3. Проверка (код)          цитата ищется в тексте; не найдена → «требует проверки»
           → 4. Расчёт (код)            веса, перераспределение при N/A, округление, флаг грубой ошибки
           → 5. Человек                 апелляция → решение проверяющего с причиной → пересчёт
Чек-лист (версии в БД) → из него собираются промпт, схема ответа и расчёт
```

- **Модель не считает баллы** — только классифицирует и цитирует. Арифметику делает код.
- **Каждый вывод проверяется:** цитата, которой нет в диалоге, снижает уверенность и отправляет критерий человеку.
- **Чек-лист — это данные:** новый или изменённый критерий применяется через интерфейс без правки кода.
- **Причины обращений:** в том же вызове модель относит диалог к причине из справочника (код «тема.подтема», справочник — данные с версиями) и отмечает исход (решён / передан / не решён / клиент ушёл). Аналитика «причина × качество» показывает, по каким причинам какие критерии проседают; из «Прочего» предлагаются новые подтемы. Код — `backend/app/reasons/`, API — `/api/reasons/*`, `/api/analytics/reasons`.
- **Персональные данные не уходят в модель:** имена (NER Natasha/slovnet + формулы «меня зовут / менің атым / my name is»), ИИН/БИН, карты, IBAN, телефоны, e-mail, даты рождения, номера документов и счетов, адреса, коды из SMS / PIN / CVV / пароли и номера, продиктованные словами в звонке, заменяются метками (`[PERSON_1]`, `[CARD_1]`…) до вызова API. В БД и в интерфейсе остаётся исходный текст, в журнал оценки пишутся только счётчики. Если детектор не загрузился, диалог не отправляется (`status: error`). Настройки `PII_MASKING`, `PII_NER`; код — `backend/app/brain/pii/`.

Подробная архитектура: [CQA_ARCHITECTURE.md](CQA_ARCHITECTURE.md).

## Запуск (Windows / macOS, нативно)

Нужны Python 3.11+ и ключ Anthropic (`ANTHROPIC_API_KEY`).

```powershell
# 1. Зависимости
pip install -r backend/requirements.txt

# 2. Настройки: скопировать и заполнить ключи (ORGANIZERS_API_URL, ANTHROPIC_API_KEY)
copy .env.example .env          # macOS/Linux: cp .env.example .env

# 3. Сервер (из папки репозитория)
cd backend
python -m uvicorn app.main:app --port 8000
```

Откройте **http://localhost:8000** → раздел «Диалоги» → «Загрузить набор» (`group_id = DEV`) → отметьте диалоги → «Оценить выбранные».

Если модель недоступна, диалог получает `status: error` с причиной — ошибка никогда не подменяется нулём. Запасной путь — любой OpenAI-совместимый API (например, Claude через OpenRouter): заполните `OPENAI_*` в `.env` и выберите его в разделе «Настройки модели».

## Запуск через Docker

```bash
cp .env.example .env            # заполнить ключи
docker compose up --build
```

Данные (SQLite) — в томе `cqa-data`, файлы `results/` — в папке репозитория.

## Прогон набора одной командой (DEV / PROD)

Из корня репозитория (PowerShell):

```powershell
$env:PYTHONPATH = "backend"

# DEV: получить набор у организаторов, оценить, выгрузить и проверить results.json
python -m app.cli run --group-id DEV --dataset DEV --checklist-version 3 --out results/dev/results.json --expect 65

# PROD (контрольный набор, ровно 10 записей). --checklist-version обязателен: results.json сдаётся
# по 8 стандартным критериям, даже если на защите критерий заменён через интерфейс (это новая версия).
# ID версии со стандартным чек-листом 1.1.0: в нашей рабочей БД — 3, в чистой БД — 1 (БД не в git);
# проверить: раздел «Чек-листы» или GET /api/checklists.
python -m app.cli run --group-id <PROD_ID> --dataset PROD --checklist-version 3 --out results/prod/results.json --expect 10
python -m app.cli validate results/prod/results.json --expect 10 --checklist-version 3
git add results/prod/results.json; git commit -m "prod results"; git push
```

bash: `PYTHONPATH=backend python -m app.cli run ...`.

Другие команды: `status` (модель и ключи), `fetch` (только загрузить набор), `export` (выгрузить results.json из БД; `--ai-only` — без решений по апелляциям), `validate`, `discover-reasons` (предложить новые подтемы причин по обращениям из «Прочего»; `--no-llm` — без модели, `--out` — сохранить предложения). Повторный запуск берёт готовые оценки из кэша (в том числе для того же транскрипта под другим ID); `--force` — переоценить. После записи CLI печатает число записей `ok` / `error`: запись `error` формально валидна, но означает, что диалог не оценён.

## Модель и стоимость

| Модель | Цена за 1 млн токенов (вход / выход) | Роль |
|---|---|---|
| **`claude-opus-5-5`**, effort `medium` | $4 / $20, чтение кэша $0.20 | по умолчанию |
| `claude-sonnet-5-5` | $2 / $10 | дешевле (`ANTHROPIC_MODEL`) |

**Стоимость одной оценки (Claude Opus 5.5, один вызов на диалог): ≈ $0.04 за чат, ≈ $0.06 за звонок.** Системный промпт с чек-листом (~9 тыс. токенов) кэшируется: первый вызов дороже на ~$0.04, дальше он читается из кэша за ~$0.002. 10 чатов PROD ≈ $0.40. Фактическая стоимость каждой оценки считается по полям `usage` и показана в карточке диалога и в «Аналитике».

**Время:** ~12 с на чат и ~20 с на звонок; 4 диалога параллельно (`CLOUD_CONCURRENCY`).

**Почему Opus.** Сравнение на размеченном наборе `eval/synt_dataset` (60 чатов RU/KZ/EN, `python eval/score_vs_gold.py`): Opus 5.5 — 95.2% совпадения по критериям, средняя ошибка итога 3.0 балла, все 6 грубых нарушений найдены без ложных срабатываний; Sonnet 5.5 — 92.1% и 4.0 балла за $0.017 за диалог. Эталон размечен ИИ, а не людьми, поэтому 95% — оценка сверху. Подробности: [eval/runs/2026-11-08_synt_claude/REPORT.md](eval/runs/2026-11-08_synt_claude/REPORT.md).

## Сценарий демо (5 минут)

1. **Диалоги** → карточка диалога: расшифровка с номерами реплик, для звонка — плеер.
2. Оценка: итог, секции, «Почему снижена оценка», по каждому критерию — ответ, баллы / вес, обоснование, цитата со статусом проверки, ссылка на реплику (клик прокручивает расшифровку и перематывает запись), пример **N/A** с перераспределённым весом.
3. «Оспорить оценку» → **Апелляции**: проверяющий видит оценку, комментарий и фрагмент, меняет оценку с причиной → новый итог; в карточке видны исходная оценка, решение и финал.
4. **Чек-листы**: изменить или заменить критерий → «Сохранить новую версию» → «Применить к выбранным диалогам».

## Структура

```
backend/app/        FastAPI: adapters (чат/звонок), brain (предобработка, промпт, модель-судья, проверка
                    цитат, решение), scoring, appeals, analytics, export (results.json + валидатор), cli
frontend/           HTML + CSS + JS без сборщика (стили под .cqa-root, адрес API в config.js — для Dynamics 365)
eval/               выбор модели: размеченный набор, отчёты прогонов, сравнение
results/dev|prod/   results.json для сдачи
tests/              pytest
data/               БД и исходные наборы от организаторов (не коммитятся)
```

## Встраивание в Dynamics 365

Интерфейс — набор статических файлов с относительными путями. Адрес API задаётся только в `frontend/config.js`. Карточка открывается параметром `?conversationId=<ID>` или параметром веб-ресурса D365 `?data=conversationId%3D<ID>`. Все стили — под корневым контейнером `.cqa-root` с префиксом `cqa-`; каждый экран — отдельный модуль `frontend/js/pages/*.js`.
