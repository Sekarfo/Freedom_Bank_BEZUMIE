# CQA — Conversation Quality Analytics

Прототип оценки качества диалогов операторов Freedom Broker (хакатон Freedom Broker × Data Challenge NU).

Система оценивает каждый диалог (чат или звонок, RU / KZ / EN) по настраиваемому чек-листу, доказывает каждый вывод номером реплики и цитатой, считает итог кодом по правилам чек-листа и оставляет финальное слово за человеком через апелляции.

**«Мозг»:** **Claude Opus 5.5** (`claude-opus-5-5`, режим «Облако») оценивает диалог по всему чек-листу и для каждого критерия даёт значение, номера реплик и дословную цитату → **код** проверяет цитаты по тексту, принимает финальное решение по фиксированным правилам и считает баллы. LLM никогда не считает баллы. Режимы «Локально» (Qwen3-8B / Qwen3.5-9B через Ollama или OpenRouter) и «Гибрид» остаются в настройках как вариант для закрытого контура, но по умолчанию не используются: на размеченном наборе облачная модель точнее (см. «Модели и стоимость»).

Подробная архитектура: [CQA_ARCHITECTURE.md](CQA_ARCHITECTURE.md).

## Запуск (Windows / macOS, нативно)

Нужны Python 3.11+ и ключ Anthropic (`ANTHROPIC_API_KEY`). [Ollama](https://ollama.com) — только для режимов «Локально» и «Гибрид».

```powershell
# 1. Зависимости
pip install -r backend/requirements.txt

# 2. Настройки: скопировать и заполнить ключи (ORGANIZERS_API_URL, ANTHROPIC_API_KEY, ...)
copy .env.example .env          # macOS/Linux: cp .env.example .env

# 3. (необязательно) локальная модель для режимов «Локально» / «Гибрид»
# ollama serve; ollama pull qwen3:8b

# 4. Сервер (из папки репозитория)
cd backend
python -m uvicorn app.main:app --port 8000
```

Откройте **http://localhost:8000** → раздел «Диалоги» → «Загрузить набор» (`group_id = DEV`) → отметьте диалоги → «Оценить выбранные».

По умолчанию работает режим **«Облако»** с Claude Opus 5.5. Без ключа Claude — режим **«Локально»** (переключатель в разделе «Настройки модели»). Если модель недоступна, диалог получает `status: error` с причиной — ошибка никогда не подменяется нулём.

## Запуск через Docker

```bash
cp .env.example .env            # заполнить ключи
# (необязательно) ollama serve && ollama pull qwen3:8b — только для режимов «Локально» / «Гибрид»
docker compose up --build
```

Backend в контейнере обращается к Ollama по `http://host.docker.internal:11434`. Данные (SQLite) — в томе `cqa-data`, файлы `results/` — в папке репозитория.

## Прогон набора одной командой (DEV / PROD)

Из корня репозитория (PowerShell):

```powershell
$env:PYTHONPATH = "backend"

# DEV: получить набор у организаторов, оценить, выгрузить и проверить results.json
python -m app.cli run --group-id DEV --dataset DEV --mode cloud --provider anthropic `
  --checklist-version 3 --out results/dev/results.json --expect 65

# PROD (контрольный набор, ровно 10 записей). --checklist-version обязателен: results.json сдаётся
# по 8 стандартным критериям, даже если на защите критерий заменён через интерфейс (это новая версия).
# ID версии со стандартным чек-листом 1.1.0: в нашей рабочей БД — 3, в чистой БД — 1 (БД не в git);
# проверить: раздел «Чек-листы» или GET /api/checklists.
python -m app.cli run --group-id <PROD_ID> --dataset PROD --mode cloud --provider anthropic `
  --checklist-version 3 --out results/prod/results.json --expect 10
python -m app.cli validate results/prod/results.json --expect 10 --checklist-version 3
git add results/prod/results.json; git commit -m "prod results"; git push
```

bash: `PYTHONPATH=backend python -m app.cli run ...` (перенос строки — `\`).

Другие команды: `status` (доступность Ollama и ключей), `fetch` (только загрузить набор), `export` (выгрузить results.json из БД; `--ai-only` — без решений по апелляциям), `validate`. Повторный запуск берёт готовые оценки из кэша (в том числе для того же транскрипта под другим ID); `--force` — переоценить. После записи CLI печатает число записей `ok` / `error`: запись `error` формально валидна, но означает, что диалог не оценён.

## Сравнение моделей (раздел 9 спецификации)

```powershell
python eval/make_gold_template.py        # шаблон эталона: 10 RU + 8 KZ + 7 EN + 3 звонка
# заполнить eval/gold/dev_gold.json вручную (значения "TODO" → true/false/null/ступень)
python eval/compare.py --out eval/report.md

# Сравнение готовых results.json с размеченным эталоном
python eval/score_vs_gold.py --gold eval/synt_dataset/synt_results.json --run opus=results.json
```

`compare.py` группирует оценки из БД по конфигурации (режим · модели · стратегия · чек-лист) и выводит таблицу: совпадение по критериям, точность N/A, MAE итога, precision/recall по грубым ошибкам, доля override, полезные и вредные override, нагрузка `needs_review`, стоимость, время, срез KZ, воспроизводимость.

## Модели и стоимость

| Режим | Модель | Цена за 1 млн токенов (вход / выход) |
|---|---|---|
| **Облако (по умолчанию)** | **`claude-opus-5-5`**, effort `medium` | $4 / $20, чтение кэша $0.20 |
| Облако (дешевле) | `claude-sonnet-5-5` | $2 / $10 |
| Локально / Гибрид | Qwen3-8B (Ollama) или `qwen/qwen3.5-9b` (OpenRouter) | $0 локально / ~$0.001 за диалог |

**Стоимость одной оценки (Claude Opus 5.5, один вызов на диалог): ≈ $0.04 за чат, ≈ $0.06 за звонок** — измерено 08.11.2026 на 78 чатах и 5 звонках: в среднем $0.038 и $0.058. Системный промпт с чек-листом (~9 тыс. токенов) кэшируется: первый вызов дороже на ~$0.04, дальше он читается из кэша за ~$0.002. 10 чатов PROD ≈ $0.40. Фактическая стоимость каждой оценки считается по полям `usage` и показана в карточке диалога и в «Аналитике».

**Время:** ~12 с на чат и ~20 с на звонок; 6 диалогов параллельно (`CLOUD_CONCURRENCY`), 60 чатов — около 2 минут.

**Почему Opus.** Сравнение на размеченном наборе `eval/synt_dataset` (60 чатов RU/KZ/EN, `python eval/score_vs_gold.py`): Opus 5.5 — 95.2% совпадения по критериям, средняя ошибка итога 3.0 балла, все 6 грубых нарушений найдены без ложных срабатываний; Sonnet 5.5 — 92.1% и 4.0 балла за $0.017 за диалог. Qwen3.5-9B на DEV совпал с контрольными случаями чек-листа в 24 из 32 решений, Opus — в 35 из 35. Подробности: [eval/runs/2026-11-08_synt_claude/REPORT.md](eval/runs/2026-11-08_synt_claude/REPORT.md).

## Сценарий демо (5 минут)

1. **Диалоги** → карточка диалога: расшифровка с номерами реплик, для звонка — плеер.
2. Оценка: итог, секции, «Почему снижена оценка», по каждому критерию — ответ, баллы / вес, обоснование, ссылка на реплику (клик прокручивает расшифровку и перематывает запись), пример **N/A** с перераспределённым весом.
3. «Оспорить оценку» → **Апелляции**: проверяющий видит оценку, комментарий и фрагмент, меняет оценку с причиной → новый итог; в карточке видны исходная оценка, решение и финал.
4. **Чек-листы**: изменить или заменить критерий → «Сохранить новую версию» → «Применить к выбранным диалогам».

## Структура

```
backend/app/        FastAPI: adapters (чат/звонок), brain (сигналы, промпты, модели, решение), scoring,
                    appeals, analytics, export (results.json + валидатор), cli
frontend/           HTML + CSS + JS без сборщика (стили под .cqa-root, адрес API в config.js — для Dynamics 365)
eval/               мини-эталон и сравнение конфигураций
results/dev|prod/   results.json для сдачи
tests/              pytest
data/raw/           исходные наборы от организаторов (не коммитятся)
```

## Встраивание в Dynamics 365

Интерфейс — набор статических файлов с относительными путями. Адрес API задаётся только в `frontend/config.js`. Карточка открывается параметром `?conversationId=<ID>` или параметром веб-ресурса D365 `?data=conversationId%3D<ID>`. Все стили — под корневым контейнером `.cqa-root` с префиксом `cqa-`; каждый экран — отдельный модуль `frontend/js/pages/*.js`.
