## 0. Коротко

**Проблема.** ОКК проверяет лишь малую выборку диалогов, вручную и субъективно, на трёх языках (RU/KZ/EN) и в двух каналах (чат/звонок). Выводы не подкреплены доказательствами, споры об оценках не формализованы.

**Решение.** Система, которая:
1. оценивает каждый диалог по настраиваемому чек-листу;
2. доказывает каждый вывод номером реплики и дословной цитатой;
3. считает итог детерминированно по правилам чек-листа;
4. оставляет финальное решение за человеком через апелляции;
5. даёт руководителям аналитику.

**Схема: один судья + проверка кодом + человек.**

```
Транскрипт ─► 1. Предобработка (код)     нумерация реплик, язык, подсказки-эвристики
           ─► 2. Модель-судья (1 вызов)  Claude Opus 5.5: по каждому критерию значение, номера реплик,
                                          дословная цитата, обоснование, уверенность
           ─► 3. Проверка (код)          цитата ищется в тексте; не найдена или эвристика против → «на проверку»
           ─► 4. Расчёт (код)            веса, перераспределение при N/A, округление, флаг грубой ошибки
           ─► 5. Человек                 апелляция → решение проверяющего с причиной → пересчёт
Чек-лист (версии в БД) ─► из него собираются промпт, схема ответа и расчёт (шаги 2–4)
```

**Принципы:**
- арифметику делает только код, модель баллы не считает;
- нет подтверждённого доказательства — нет уверенного вывода (флаг «требует проверки»);
- N/A ставится только там, где его разрешает чек-лист;
- чек-лист — это данные: новый критерий работает без правки кода;
- одинаковый вход даёт одинаковый результат (кэш оценок, версии промптов и чек-листа в журнале);
- ошибка — это `status: "error"`, а не ноль.

**Почему одна модель.** Модель — заменяемый компонент (адаптер Claude / OpenAI-совместимый API). Выбор сделан замером на 60 размеченных чатах (`eval/runs/2026-11-08_synt_claude/REPORT.md`): Claude Opus 5.5 — 95.2% совпадения по критериям, средняя ошибка итога 3.0 балла, все 6 грубых нарушений без ложных срабатываний, ≈ $0.04 и 12 с на чат. Двухэтапная схема с локальной моделью проверялась и отклонена: малая модель ошибалась примерно в четверти контрольных случаев, тратила минуты на диалог, а облако всё равно приходилось вызывать.

## 3. Данные

### 3.1. Вход от организаторов (храним как есть)

```json
{ "isSuccess": true, "data": { "dataset_group_id": "DEV", "total_records": 65,
  "records": [{ "conversation_id": "p1-ru-001", "channel": "agent chat",
    "language": "RU", "transcript": [{"timestamp": "00:02", "speaker": "operator", "text": "..."}],
    "audio_url": null }] } }
```

- `channel`: `agent chat` | `voice call`; `language`: `RU` | `KZ` | `EN`; `speaker`: `client` | `operator` | `bot` | `system`.
- `timestamp`: у чатов `MM:SS`, у звонков ISO 8601 с часовым поясом. **Исходные метки хранятся без изменений.**

### 3.2. Единая модель «Диалог» (после адаптера)

```python
class Turn(BaseModel):
    idx: int                 # 1..N по ИСХОДНОМУ массиву, включая client/bot/system
    speaker: Literal["client", "operator", "bot", "system"]
    text: str
    ts_raw: str              # исходная метка как пришла
    offset_sec: float | None # секунды от самой ранней метки диалога
    audio_offset_sec: float | None  # позиция в аудиозаписи (звонки)

class Conversation(BaseModel):
    conversation_id: str     # исходный ID, не трогаем
    dataset: str             # DEV | PROD | upload
    channel: Literal["chat", "voice", "email", "messenger"]
    language: Literal["RU", "KZ", "EN"]
    turns: list[Turn]
    audio_url: str | None
    is_speech: bool          # True для звонков (учитывать ошибки распознавания речи)
```

### 3.3. Адаптеры каналов

| Адаптер | Особенности |
|---|---|
| `ChatAdapter` | `MM:SS` → `offset_sec`; `audio_url = None` |
| `VoiceAdapter` | ISO 8601 → `offset_sec`; `audio_offset_sec` — от события «Запись запущена» за вычетом пауз записи; `is_speech=True` |
| Будущее: `EmailAdapter`, `MessengerAdapter` | Добавляются без изменения конвейера |

**Правило:** `idx` присваивается по порядку исходного массива, без перестановок и фильтраций — иначе `evidence_turns` в `results.json` будут неверными.

**Запись звонка.** `audio_url` у организаторов — HTML-страница с плеером; внутри неё mp3 с подписью, которая живёт ~1 час. Backend отдаёт `GET /api/conversations/{id}/audio` → 307 на свежую mp3-ссылку (кэш 40 минут), кнопка «Открыть запись в новой вкладке» ведёт на исходную страницу.

## 4. Чек-лист как конфигурация

Чек-лист хранится в БД с версиями. Системный промпт и JSON-схема ответа **собираются из выбранной версии** (`render.py`). Поэтому замена критерия делается в разделе «Чек-листы» без правки кода: «Сохранить новую версию» → «Применить к выбранным диалогам». Старые оценки остаются привязаны к своей версии.

### 4.1. Схема критерия

```json
{
  "criterion_id": "identification",
  "title": "Идентификация",
  "section": "Безопасность и решение",
  "weight": 20,
  "type": "binary",                 // "binary" | "scale"
  "scale": null,                    // для scale: [{"value":20,"description":"..."}, ...]
  "na_allowed": true,
  "yes_definition": "...", "no_definition": "...", "na_condition": "...",
  "guidance": "Порядок решения, пограничные случаи, особенности звонков (попадает в промпт)",
  "is_critical_flag": false,        // true только для critical: без веса, отдельный флаг
  "channels": ["chat", "voice"]
}
```

`default_checklist.json` написан в подробном формате (определения, порядок решения, пограничные случаи, частые ошибки оценщика, особенности звонков); при первом запуске он сворачивается в поля выше (`render.convert_rich_criteria`) и становится версией 1.

### 4.2. Чек-лист по умолчанию (из PDF, коды из приложения)

| criterion_id | Название | Значения | N/A | Вес |
|---|---|---|---|---|
| `contact` | Установление контакта | true/false | нет | 10 |
| `discovery` | Выявление потребности | true/false/null | да | 15 |
| `identification` | Идентификация | true/false/null | да | 20 |
| `consultation` | Корректная и полная консультация | 0, 5, 10, 15, 20 / null | да | 20 |
| `empathy` | Эмпатия и клиентоориентированность | true/false | нет | 15 |
| `dialogue` | Управление диалогом, скорость, грамотность | 0, 4, 7, 10 | нет | 15 |
| `closure` | Завершение | true/false/null | да | 5 |
| `critical` | Грубые ошибки | true/false | нет | — (флаг) |

### 4.3. Общие правила (в системном промпте)

- оценивается **оператор**; бот и системные события — контекст;
- «Нет» — действие было нужно, но пропущено или сделано неправильно; N/A — критерий неприменим по условию;
- у каждого вывода — номер реплики и дословная цитата на языке оригинала; для пропущенного действия — место, где оно ожидалось; для N/A — реплика, подтверждающая условие;
- обоснования на русском; при недостатке информации — `confidence: low` и объяснение, без выдуманных фактов;
- звонки: не штрафовать за ошибки распознавания речи, обрывки и повторы; «[Имя скрыто]» = оператор назвал имя.

## 5. Расчёт итога (только код)

```python
def compute_score(results, checklist) -> float | None:
    earned, applicable = 0, 0
    for c in checklist.criteria:
        if c.is_critical_flag:
            continue                          # без веса
        v = results[c.criterion_id]
        if v is None:                         # N/A → критерий исключается, вес перераспределяется
            continue
        applicable += c.weight
        earned += (c.weight if v is True else 0) if c.type == "binary" else v / max_scale(c) * c.weight
    return None if applicable == 0 else round_half_up(earned / applicable * 100, 2)
```

Считается на дробях (`Fraction`), округление half-up до двух знаков. Если после замены критерия сумма весов не 100, итог всё равно нормируется к 100.

| Случай | Ожидание |
|---|---|
| Пример из приложения: contact=true, discovery=null, identification=null, consultation=15, empathy=true, dialogue=7, closure=true | **85.38** (55.5 / 65 × 100) |
| Всё «Да» и максимум шкал | 100.0 |
| Все взвешенные критерии N/A | `None` |
| `critical=true` | итог не меняется, флаг отдельно |

Итоги секций считаются той же формулой по своим критериям.

## 6. Конвейер оценки

### 6.1. Шаг 1 — предобработка (код)

Нумерованный транскрипт `[idx] speaker (ts): text`, первая реплика оператора, язык клиента и оператора и **подсказки-эвристики** по словарям RU/KZ/EN (`signals.py`): приветствие, представление, прощание, шаблоны грубых нарушений, системные события верификации, признаки обрыва чата. Подсказки передаются модели с пометкой «могут ошибаться» и используются на шаге 3 для оценки уверенности. Вердиктами они не являются.

**Маскирование персональных данных** (`brain/pii/`, `PII_MASKING=true`, `PII_NER=slovnet`). Эвристики считаются локально по исходному тексту, а в модель уходит копия транскрипта, где значения заменены метками.

| Детектор | Что находит | Как отсекаются ложные срабатывания |
|---|---|---|
| `rules.py` | `SECRET` (код из SMS, PIN, CVV, пароль, кодовое слово), `EMAIL`, `IBAN`, `PHONE`, `CARD`, `IIN`, `DOB`, `DOC`, `ACCOUNT`, `ADDRESS`, `NUMBER` (сплошные номера от 10 цифр) | mod 97 для IBAN, алгоритм Луна для карт, контрольный разряд ИИН; дата рождения, документ, счёт, код — только рядом с ключевым словом; суммы с валютой, даты и время не трогаются |
| `spoken.py` | номера словами и группами цифр в звонке: «восемь семьсот один сто двадцать три…», «сегіз жеті жүз бір…», «eight seven oh one…», «900 101 300 017» | серия собирается в цифры по правилам устной речи и классифицируется (телефон / ИИН / карта / номер); от 7 цифр словами и от 10 цифрами; за серией не должна идти валюта или «тысяч» |
| `names.py` | `PERSON`: NER slovnet (проект Natasha, CPU, без сети) + контекст RU/KZ/EN («меня зовут», «я», «менің атым», «мен», «my name is», «I'm», «оператор …») + ФИО с отчеством (-ович/-овна/-ұлы/-қызы, с падежами) | стоп-лист брендов и служебных слов; одиночное слово NER в начале предложения не принимается (русская модель на казахском тексте принимает за имя первое слово фразы), внутри «кавычек» — названия пунктов меню |

При пересечении побеждает более сильный тип (`SECRET` > `EMAIL` > `IBAN` > `CARD` > `IIN` > `PHONE` > … > `PERSON` > `NUMBER`), уже скрытые фрагменты в квадратных скобках («[Имя скрыто]») не трогаются. Одинаковое значение в диалоге получает одну метку (`+7 701…` и `8 701…` — один `[PHONE_1]`). Найденное имя скрывается и в остальных репликах, в том числе склонённое и в нижнем регистре («спасибо, алина»). Соответствие «метка → значение» существует только в памяти на время оценки. Если в диалоге что-то замаскировано, в пользовательский промпт добавляется пояснение: метка означает реальное значение («меня зовут [PERSON_1]» — оператор представился, `[ACCOUNT_1]` до подтверждения личности — раскрытие данных, запрос `[SECRET_1]` — запрос секретных данных). Цитаты модели сверяются с тем же замаскированным текстом. В журнал (`audit.masking`) пишутся только счётчики по типам и источникам и номера реплик.

**Fail-closed:** если маскирование включено, а NER не загрузился, оценка завершается `status: error` без вызова модели; состояние видно в `GET /api/system/status` и в логе при старте. Проверка на `eval/synt_dataset` (60 чатов, 916 реплик): все 57 представлений операторов скрыты, ложных срабатываний нет, ~25 мс на диалог. Не распознаются адреса без ключевого слова («живу на Абая 150»), имена без контекста в начале фразы на казахском и номера, продиктованные вперемешку со словами-паразитами.

### 6.2. Шаг 2 — модель-судья (один вызов на диалог)

- **Системный промпт** (`prompts/judge_system.md`): роль специалиста ОКК, общие правила, отрендеренный чек-лист. Одинаков для всех диалогов одной версии чек-листа → у Claude помечен `cache_control` (со второго вызова читается из кэша за ~$0.002).
- **Пользовательский промпт:** метаданные (канал, язык), особенности звонка, подсказки, транскрипт.
- **Ответ** по JSON-схеме: блок `facts` (реплика с запросом, было ли защищённое действие, где раскрыты данные счёта, где подтверждена личность, была ли жалоба), затем `criteria` — массив по одному объекту на критерий:

```json
{"criterion_id": "contact", "evidence_turns": [3], "quote": "Здравствуйте! Чем могу помочь?",
 "rationale": "Поздоровался, но не представился в первом ответе.", "value": false, "confidence": "high"}
```

Порядок полей: доказательство → рассуждение → значение. Схема — массив с общей схемой элемента (`criterion_id` из enum кодов чек-листа): схема с отдельным объектом на каждый критерий даёт у Claude `400: compiled grammar is too large`. Допустимые значения конкретного критерия проверяет код (мягкое приведение `"true"` / `"N/A"` / `"15"`); при ошибке — **один** повтор с текстом ошибки, валидные критерии первой попытки сохраняются.

**Claude:** `output_config.format = {"type": "json_schema", ...}`, глубина рассуждения `output_config.effort` (`ANTHROPIC_EFFORT=medium`), серверный fallback при отказе модели (beta `server-side-fallback-2026-07-01`). Принудительный `tool_choice` и `temperature` у Opus/Sonnet 5.5 возвращают 400 и не используются.
**OpenAI-совместимый API** (запасной путь, например Claude через OpenRouter): Structured Outputs (`json_schema`, `strict`).

| Модель | Цена, $ за 1 млн токенов (вход / выход) | Роль |
|---|---|---|
| `claude-opus-5-5` | 4 / 20, чтение кэша 0.20 | по умолчанию |
| `claude-sonnet-5-5` | 2 / 10 | дешевле, точность на 3 п.п. ниже |

Стоимость считается только по полям `usage` ответа и показывается в карточке и аналитике.

### 6.3. Шаг 3 — проверка и решение (код, `decision.py`)

Значение модели не меняется; код решает, можно ли ему доверять без человека.

| Ситуация | Уверенность | `needs_review` |
|---|---|---|
| Цитата найдена в указанной реплике (или в другой — тогда номер исправляет код) | как у модели | если low |
| Цитата не найдена в тексте диалога | low | **да** |
| Модель сама указала `confidence: low` | low | **да** |
| Эвристика явно противоречит значению (например, «меня зовут» в первой реплике, а `contact=false`) | на ступень ниже | если стала low |
| `critical = false`, но словарь нашёл грубую фразу | как есть | **да** («возможное нарушение») |
| Нет валидного значения хотя бы по одному критерию после повтора | — | диалог → `status: "error"` |

**Статусы доказательства** (`evidence.py`): `verified` — цитата найдена в указанной реплике (нормализация регистра и пробелов, нечёткое совпадение ≥ 0.85); `corrected` — найдена в другой реплике, номер исправлен кодом; `no_quote`, `unverified`, `missing` — не подтверждено. Если номеров нет, подставляется проверенный участок по умолчанию (`default`: первая реплика оператора для `contact`, последняя — для `closure` и т.д.), чтобы `evidence_turns` не был пустым.

### 6.4. Шаг 4 — расчёт (раздел 5) и журнал

Журнал каждой оценки: модель, версия промпта, хеш чек-листа, факты, сырой ответ модели, токены, стоимость, время каждого шага.

### 6.5. Шаг 5 — апелляции

Решение проверяющего не перезаписывает исходную оценку. По каждому критерию хранятся три слоя: `ai_value` (оценка ИИ) → `review` (действие `confirm | change`, новое значение, причина, кто, когда) → `value` (финал). Итог пересчитывается по финальным значениям. В карточке видны все три слоя.

### 6.6. Воспроизводимость и кэш

- Ключ кэша: `sha256(реплики + канал + язык + хеш критериев + хеш справочника причин + провайдер + модель + effort + версии промптов)`; версия маскирования добавляется, только если маскирование изменило текст диалога (для остальных диалогов прежний кэш в силе). Повторный запуск с тем же ключом возвращает сохранённую оценку (задача считает `from_cache`); «Переоценить» / `--force` — пересчитать.
- Тот же транскрипт под другим ID (например, PROD повторяет DEV) получает копию оценки без вызова модели и без чужих решений по апелляциям.
- Ошибки и неполные оценки не кэшируются — следующий запуск попробует снова.

### 6.7. Причины обращений (`reasons/`)

**Справочник** — данные с версиями, как чек-лист (таблица `reason_taxonomy_versions`, стартовый — `reasons/default_taxonomy.json`: 9 тем, 27 подтем). Код причины — «тема.подтема» (`money.withdrawal`); `other.other` обязателен и добавляется сам. Активная версия — из настроек (`reason_taxonomy_version_id`), иначе последняя; задача оценки фиксирует версию при создании.

**Классификация — в том же вызове модели-судьи**, без отдельного запроса. Справочник рендерится в системный промпт (кэшируется, ~1,5 тыс. токенов), в схеме ответа между `facts` и `criteria` — блок `reason`: `primary` (код из перечня), `secondary` (другие вопросы клиента), `other_description` (суть, если `other.other`), `resolution` (`resolved | escalated | unresolved | client_left | no_request`). Код проверяет ответ (`normalize_reason`): неизвестный код → `other.other` с записью в `issues`. На баллы причина не влияет, поэтому ошибка в ней не делает оценку `status: error` и не вызывает повтор. Хранится в оценке: `reason_code`, `reason_topic`, `resolution` (индексируются), полный разбор `reason`, версия справочника; копия оценки для того же транскрипта переносит причину. В `results.json` не выгружается — формат организаторов не меняется.

**Аналитика** (`GET /api/analytics/reasons`, последняя оценка каждого диалога): по теме и подтеме — объём, доля, средний балл, исходы, грубые нарушения, «на проверку», три самых слабых критерия; матрица «причина × критерий» (`level=topic|subtopic`; доля от максимума, для `critical` — доля нарушений); **находки** — где критерий по причине на 15+ п.п. ниже среднего при ≥3 диалогах, отсортированы по влиянию («Вывод средств: эмпатия 0% против 50%»); доп. причины; описания из «Прочего».

**Новые подтемы** (`POST /api/reasons/discover`, CLI `discover-reasons`): описания из «Прочего» группируются одним вызовом модели (по смыслу, на любом языке; заодно находит обращения, которые подходят под существующую подтему) или без модели — по общим основам слов. Ответ модели проверяется кодом (формат кодов, номера, порог размера кластера). Справочник не меняется сам: в ответе — предложения с примерами и готовый `proposed_topics`, который после просмотра сохраняется новой версией.

### 9.3. Проверки `results.json` перед push (`validator.py`)

UTF-8, валидный JSON; `schema_version = "1.0"`, `team_name`, `model.mode`, `model.name`; одна запись на диалог без дубликатов, ID совпадают с API; в prod **ровно 10** записей; `status = "ok"` — все критерии ровно по одному разу, значения из допустимого набора; `status = "error"` — `criteria = []`, `score = null`, заполнен `error`; `final_score` 0–100, два знака; `critical_flag` равен `value` критерия `critical`.

Если на защите критерий заменён, `results/prod/results.json` выгружается по **исходным 8 кодам** (`--checklist-version` с версией 1.1.0): приложение запрещает менять коды критериев.

### 9.4. Тесты

Маскирование персональных данных (каждый тип, номера словами, имена, ложные срабатывания, распространение имён, fail-closed, в модель и в журнал не попадают значения); калькулятор; адаптеры (метки времени как есть, `idx` по исходному массиву); `evidence.py`; каждая строка таблицы 6.3; конвейер с mock-моделью (повтор при невалидном ответе, ошибка модели → `status: error`); задачи, кэш, апелляции, экспорт и валидатор; сквозной сценарий через HTTP API.

## 10. Прогон контрольного набора (за час до стоп-кода)

```bash
export PYTHONPATH=backend          # PowerShell: $env:PYTHONPATH="backend"
python -m app.cli run --group-id <PROD_ID> --dataset PROD --checklist-version <ID версии 1.1.0> \
  --out results/prod/results.json --expect 10
python -m app.cli validate results/prod/results.json --expect 10 --checklist-version <ID>
git add results/prod/results.json && git commit -m "prod results" && git push
```

`run` сам валидирует файл и возвращает код 1 при ошибках. Если API организаторов недоступен, используется последняя копия из `data/raw/`. 10 чатов ≈ 2 минуты и ≈ $0.40. Если модель упала на диалоге — `status: "error"`, запись не пропадает; повторный `run` переоценит только упавшие.

## 13. Трактовки правил, принятые командой (меняются через редактор чек-листа)

Записаны в `default_checklist.json` (v1.1.0) и попадают в промпт. Если жюри трактует иначе — правим текст в разделе «Чек-листы» и сохраняем новую версию, код не меняется.

| Критерий | Трактовка |
|---|---|
| `identification` | Запрос требовал проверки личности, а подтверждения в чате нет — «Нет», даже если данные не раскрыты (буква PDF). N/A — только если запрос проверки не требовал. |
| `critical` | Сведения о конкретном счёте, сообщённые до подтверждения личности, — раскрытие конфиденциальной информации, `critical = true`. |
| `closure` | Нужны оба условия: (итог или предложение дальнейшей помощи) **и** прощание. «Пожалуйста. Хорошего дня!» после «спасибо» — «Нет». |
| `consultation` | Не снижать до 15 за детали, о которых клиент не спрашивал; передача вопроса специалистам без срока — корректный следующий шаг. |
| `discovery` | Уточнять было нечего и оператор сразу ответил по существу — N/A, а не «Да». |
| `contact` | «[Имя скрыто]» в звонках = оператор представился (имя скрыто анонимизацией). |
