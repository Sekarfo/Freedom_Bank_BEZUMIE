## 0. Коротко

**Проблема.** ОКК проверяет лишь малую выборку диалогов, вручную и субъективно, на трёх языках (RU/KZ/EN) и в двух каналах (чат/звонок). Выводы не подкреплены доказательствами, споры об оценках не формализованы.

**Решение.** Омниканальная система, которая:
1. оценивает каждый диалог по настраиваемому чек-листу;
2. доказывает каждый вывод номером реплики и цитатой;
3. считает итог детерминированно по правилам чек-листа;
4. оставляет финальное решение за человеком через апелляции;
5. даёт руководителям аналитику.

**«Мозг» — гибрид в два этапа:**
1. **локальная модель** (Qwen3-8B) делает первичную оценку;
2. **облачная модель** (Claude или OpenAI, выбирается переключателем) проверяет и подтверждает или исправляет оценку;
3. **код** принимает финальное решение по фиксированным правилам и считает баллы.

**Принципы, которые нельзя нарушать:**
- арифметику делает только код, LLM никогда не считает баллы;
- нет доказательства — нет уверенного вывода (флаг «требует проверки»);
- N/A ставится только там, где его разрешает чек-лист;
- одинаковый вход даёт одинаковый результат (temperature 0 у локальной модели и OpenAI, кэш результатов, версии в журнале; у Claude Sonnet/Opus 5.5 параметра temperature нет — см. 6.8);
- ошибка — это `status: "error"`, а не ноль.

## 3. Данные

### 3.1. Вход от организаторов (не меняем, храним как есть)

```json
{ "isSuccess": true, "data": { "dataset_group_id": "DEV", "total_records": 65,
  "records": [{ "conversation_id": "p1-ru-001", "channel": "agent chat",
    "language": "RU", "transcript": [{"timestamp": "00:02", "speaker": "operator", "text": "..."}],
    "audio_url": null }] } }
```

- `channel`: `agent chat` | `voice call`
- `language`: `RU` | `KZ` | `EN`
- `speaker`: `client` | `operator` | `bot` | `system`
- `timestamp`: у чатов `MM:SS`, у звонков ISO 8601 с часовым поясом. **Исходные метки хранить без изменений.**

### 3.2. Единая модель «Диалог» (после адаптера)

```python
class Turn(BaseModel):
    idx: int                 # 1..N по ИСХОДНОМУ массиву, включая client/bot/system
    speaker: Literal["client", "operator", "bot", "system"]
    text: str
    ts_raw: str              # исходная метка как пришла
    offset_sec: float | None # секунды от самой ранней метки диалога
    audio_offset_sec: float | None  # позиция в аудиозаписи (звонки): от старта записи минус паузы записи

class Conversation(BaseModel):
    conversation_id: str     # исходный ID, не трогаем
    dataset: str             # DEV | PROD | upload
    channel: Literal["chat", "voice", "email", "messenger"]
    language: Literal["RU", "KZ", "EN"]
    turns: list[Turn]
    audio_url: str | None
    is_speech: bool          # True для звонков (учитывать ошибки ASR)
    raw: dict                # исходная запись целиком
```

### 3.3. Адаптеры каналов (омниканальность)

```python
class ChannelAdapter(Protocol):
    channel_codes: set[str]                # что умеет: {"agent chat"}
    def normalize(self, record: dict) -> Conversation: ...
```

| Адаптер | Особенности |
|---|---|
| `ChatAdapter` | `MM:SS` → `offset_sec`; `audio_url = None` |
| `VoiceAdapter` | ISO 8601 (7 знаков дроби) → `offset_sec` от самой ранней метки; `audio_offset_sec` — от события «Запись и транскрибирование запущены» за вычетом интервалов «приостановлены → возобновлены» (допущение: в паузе звук не пишется — сверить на слух); сохраняет `audio_url`; ставит `is_speech=True` |
| Будущее: `EmailAdapter`, `MessengerAdapter` | Добавляются без изменения конвейера |

**Правило:** `idx` присваивается по порядку исходного массива. Никаких перестановок и фильтраций до нумерации — иначе `evidence_turns` в `results.json` будут неверными. (В DEV-звонках метки бывают одинаковыми и не по порядку, например «Клиент завершил разговор» стоит перед последней репликой клиента, — порядок массива всё равно не меняем.)

**Запись звонка.** `audio_url` у организаторов — это HTML-страница с плеером, а не аудиофайл; внутри неё `<source src>` с mp3 на Dynamics с подписью, которая живёт ~1 час. Поэтому backend отдаёт `GET /api/conversations/{id}/audio` → 307 на свежую mp3-ссылку (кэш 40 минут), а кнопка «Открыть запись в новой вкладке» ведёт на исходную страницу (`/audio-page`).

## 4. Чек-лист как конфигурация

Чек-лист хранится как JSON с версиями. Промпты **собираются из конфига**, а не зашиты в код. Поэтому замена критерия на контрольной проверке делается через интерфейс без правки кода.

### 4.1. Схема критерия

```json
{
  "criterion_id": "identification",
  "title": "Идентификация",
  "section": "Безопасность и решение",
  "weight": 20,
  "type": "binary",                 // "binary" | "scale"
  "scale": null,                    // для scale: [{"value":20,"description":"..."}, ...]
  "na_allowed": true,
  "yes_definition": "Проверка личности подтверждена до раскрытия данных или защищённого действия.",
  "no_definition": "Требовалась проверка перед защищённым действием, но она не подтверждена в чате.",
  "na_condition": "Запрос не требовал идентификации (например, общий вопрос о тарифах).",
  "guidance": "Подтверждение может быть в системном сообщении.",
  "is_critical_flag": false,        // true только для critical: без веса, отдельный флаг
  "channels": ["chat", "voice"]
}
```

### 4.2. Чек-лист по умолчанию (из PDF, коды из приложения)

| criterion_id | Название | Тип / значения | N/A | Вес |
|---|---|---|---|---|
| `contact` | Установление контакта | true/false | нет | 10 |
| `discovery` | Выявление потребности | true/false/null | да | 15 |
| `identification` | Идентификация | true/false/null | да | 20 |
| `consultation` | Корректная и полная консультация | 0, 5, 10, 15, 20 / null | да | 20 |
| `empathy` | Эмпатия и клиентоориентированность | true/false | нет | 15 |
| `dialogue` | Управление диалогом, скорость, грамотность | 0, 4, 7, 10 | нет | 15 |
| `closure` | Завершение | true/false/null | да | 5 |
| `critical` | Грубые ошибки | true/false | нет | — (флаг) |

### 4.3. Правила по критериям (это идёт в промпты)

**contact (10).** «Да» требует **двух** условий: оператор поздоровался **на языке клиента** и **представился в первом ответе**. Приветствие бота не засчитывается. Если клиент пишет на KZ, а оператор отвечает на RU, ставится «Нет». Доказательство — первая реплика оператора. При «Нет» указать, чего не хватило.

**discovery (15).** «Да» — оператор учёл известные детали и уточнил недостающее **до ответа**. N/A — данных для ответа хватало с самого начала. «Нет» — для ответа не хватало данных, а оператор не уточнил их или проигнорировал уже сказанное клиентом.

**identification (20).** «Да» — проверка личности подтверждена **до** раскрытия данных или защищённого действия. Подтверждение может быть в `system`-сообщении. N/A — запрос не требовал идентификации. «Нет» — требовалась проверка перед защищённым действием, и она не подтверждена в чате.

**consultation (0–20).** Шкала:
- 20 — все существенные вопросы закрыты или дан корректный следующий шаг;
- 15 — основной вопрос решён, пропущена второстепенная деталь;
- 10 — часть запроса закрыта, существенный вопрос остался открытым;
- 5 — есть общая подсказка, но клиенту всё ещё непонятно, как действовать;
- 0 — ответа по существу нет или ключевая рекомендация ошибочна.

N/A — **только** если чат закончился до того, как клиент сформулировал запрос.

**empathy (15).** «Да» — оператор вежлив и, если клиент выразил недовольство или описал неудобство, **отреагировал на конкретную проблему**. Дежурная фраза на конкретную жалобу — «Нет». N/A нет.

**dialogue (0–10).** Шкала:
- 10 — ответы ясные и связные; при явном ожидании оператор предупредил;
- 7 — один заметный сбой, но клиент может понять ответ и продолжить;
- 4 — клиенту приходится переспрашивать из-за формулировок или порядка ответов;
- 0 — из-за бессвязных или противоречивых реплик ход диалога непонятен.

N/A нет. Порог первой реакции 3 минуты, теги и вложения в оценку **не входят**.

**closure (5).** «Да» — подвёл итог или предложил дальнейшую помощь **и** попрощался. N/A — чат оборвался до возможности его завершить. «Нет» — была возможность, но оператор закрыл чат без прощания.

**critical (флаг, без баллов).** «Да», если есть хотя бы одно:
- оскорбление клиента;
- предложение платной услуги в обход компании: перевести деньги оператору лично для инвестирования или дать личный номер для платной частной консультации;
- раскрытие конфиденциальной информации.

**Достаточно самого предложения**, согласие клиента или перевод не нужны. Флаг **не обнуляет** итог.

**Общие правила для всех критериев:**
- оценивается **оператор**; бот и системные события служат контекстом;
- «Нет» — действие было нужно, но пропущено или сделано неправильно; N/A — критерий неприменим по условию;
- у каждого вывода должны быть номер реплики и короткая цитата; для пропущенного действия — место, где оно ожидалось; для N/A — какое условие неприменимости выполнено;
- для звонков (`is_speech=True`) не штрафовать за ошибки распознавания речи, обрывки и повторы, типичные для устной речи.

## 5. Расчёт итога (только код)

```python
def compute_score(results: dict[str, int | bool | None], checklist) -> float | None:
    earned, applicable = 0.0, 0.0
    for c in checklist.criteria:
        if c.is_critical_flag:
            continue                          # без веса
        v = results[c.criterion_id]
        if v is None:                         # N/A → критерий исключается
            continue
        applicable += c.weight
        if c.type == "binary":
            earned += c.weight if v is True else 0.0
        else:                                 # scale: верхняя ступень = полный вес
            earned += v / max(s.value for s in c.scale) * c.weight
    if applicable == 0:
        return None                           # итог не рассчитывается
    return round(earned / applicable * 100, 2)
```

**Обязательные тесты:**

| Случай | Ожидание |
|---|---|
| Пример из приложения: contact=true, discovery=null, identification=null, consultation=15, empathy=true, dialogue=7, closure=true | **85.38** (55.5 / 65 × 100) |
| Всё «Да» и максимум шкал | 100.0 |
| Все взвешенные критерии N/A (теоретически) | `None` |
| dialogue=4 при весе 15 | 6.0 баллов |
| `critical=true` | итог не меняется, флаг отдельно |

Отображение в UI: «баллы / вес» по критерию (например, «10.5 / 15»), круговой итог, итоги по секциям. Секция считается той же формулой по своим критериям.

## 6. «Мозг»: гибридный конвейер

### 6.1. Режимы (переключатель в интерфейсе и параметр API)

| `mode` | Что происходит |
|---|---|
| `local` | Только этап 1, затем код (этап 3 без облака) |
| `cloud` | Только облачная модель в роли первичного судьи, затем код |
| `hybrid` (**по умолчанию**) | Локальная оценка → облачная проверка → решение кодом |

`cloud_provider`: `anthropic` | `openai`. `local_model`: `qwen3-8b` | `qwen3.5-9b`.

### 6.2. Схема

```
Conversation + ChecklistVersion
        │
        ▼
[Этап 0] preprocess (код)
  - нумерация реплик [idx] speaker: text
  - первая реплика оператора, язык клиента и оператора
  - NLP-сигналы: приветствие, представление, прощание, шаблоны грубых нарушений,
    системные события верификации, признаки обрыва чата
        │
        ▼
[Этап 1] LOCAL — Qwen3-8B / Qwen3.5-9B
  - извлечение фактов + предварительный вердикт по каждому критерию
  - JSON по схеме: value, rationale, evidence_turns, quote, confidence
        │
        ▼
[Этап 2] CLOUD — Claude или OpenAI
  - «старший специалист ОКК»: проверяет каждый вердикт локальной модели
  - по каждому критерию: confirm | override + причина + доказательство
        │
        ▼
[Этап 3] DECISION (код)
  - валидация обоих ответов, проверка цитат
  - финальный вердикт, уверенность, флаг needs_review
        │
        ▼
[Этап 4] SCORING (код) → [Этап 5] сохранение + журнал аудита
```

### 6.3. Этап 0 — предобработка и NLP-сигналы

Сигналы — **подсказки**, а не вердикты. Они передаются обеим моделям и используются в этапе 3 для оценки уверенности.

```python
class Signals(BaseModel):
    first_operator_idx: int | None
    client_lang: str | None          # по полю language + (опционально) детектор по репликам
    operator_lang_first_turn: str | None
    greeting_turns: list[int]        # словари: здравствуйте / сәлеметсіз бе / hello ...
    intro_turns: list[int]           # "меня зовут" / "менің атым" / "my name is" ...
    farewell_turns: list[int]
    critical_pattern_turns: list[int]# "переведите мне на карту", "мой личный номер" ...
    verification_system_turns: list[int]
    chat_ended_abruptly: bool        # последняя реплика клиента без ответа / системное закрытие
```

Словари RU/KZ/EN держим в `signals.py` и дополняем по мере просмотра DEV.

### 6.4. Этап 1 — локальная модель

**Кандидаты:**

| Модель | Запуск | Примечание |
|---|---|---|
| Qwen3-8B | `ollama pull qwen3:8b` или vLLM | Лучший средний ранг среди моделей ~8B на казахских бенчмарках в исследовании 2026 года (Information, MDPI) |
| Qwen3.5-9B | vLLM / SGLang / Transformers (`Qwen/Qwen3.5-9B`); тег в Ollama — проверить | Новее (февраль 2026), контекст 262K; содержит vision encoder, поэтому памяти нужно больше. Прямых данных по казахскому не нашли |

**Выбор между ними — по замеру в первые часы** (раздел 9.2), а не по бенчмаркам.

**Настройки:** `temperature=0`, `seed=42`, ограничение длины ответа, `num_ctx` по длине промпта: 8K для чатов, `LOCAL_NUM_CTX` (16K) для звонков; если ответ упёрся в контекст — автоматический повтор со следующей ступенью. Ступеней две, потому что смена `num_ctx` перезагружает модель в Ollama (~45 с). Меньше контекст → меньше KV-кэш → больше слоёв в видеопамяти. JSON по схеме:
- Ollama (`LOCAL_LLM_BACKEND=ollama`): нативный `/api/chat`, параметр `format` с JSON-схемой (constrained decoding);
- vLLM (`LOCAL_LLM_BACKEND=openai`): `response_format` с `json_schema`.

**Схема ответа** строится из чек-листа: объект с ключом на каждый `criterion_id` (модель не может пропустить критерий), допустимые значения зашиты в схему (`enum` ступеней шкалы, `null` только при `na_allowed`). Порядок полей внутри критерия: `evidence_turns` → `quote` → `rationale` → `value` → `confidence` — модель сначала находит доказательство, потом выносит значение. Перед критериями — блок `facts`.

**Режим рассуждения у Qwen.** Проверить оба варианта: с рассуждением качество обычно выше, но ответ дольше. В vLLM он управляется через `chat_template_kwargs={"enable_thinking": ...}`, в Ollama — через параметр `think` (`LOCAL_THINK`, по умолчанию `false`).

**Выход этапа 1:**

```json
{
  "criteria": [
    {"criterion_id": "contact", "value": false,
     "rationale": "Оператор поздоровался, но не представился в первом ответе.",
     "evidence_turns": [3], "quote": "Здравствуйте! Чем могу помочь?",
     "confidence": "high"}
  ],
  "facts": {"client_request_turn": 2, "protected_action_requested": false,
            "complaint_present": false, "verification_confirmed_turn": null}
}
```

### 6.5. Этап 2 — облачная модель

**Роль:** проверяющий поверх локальной оценки. Видит транскрипт, чек-лист, сигналы и вердикты этапа 1.

**Выход этапа 2:**

```json
{
  "criteria": [
    {"criterion_id": "contact", "decision": "confirm",
     "value": false, "rationale": "...", "evidence_turns": [3],
     "quote": "Здравствуйте! Чем могу помочь?", "confidence": "high"},
    {"criterion_id": "consultation", "decision": "override",
     "value": 10, "override_reason": "Срок ответа по обращению не назван (реплика 7).",
     "rationale": "...", "evidence_turns": [6, 7], "quote": "...", "confidence": "medium"}
  ]
}
```

**Структурированный вывод:**
- Облачным моделям отдаётся **компактная схема**: `criteria` — массив с одной общей схемой элемента (`criterion_id` из enum, `value: boolean | integer | null`). Полная схема с отдельным объектом на каждый критерий даёт у Claude `400: The compiled grammar is too large` (проверено 07.11.2026). Допустимые значения конкретного критерия проверяет код; при ошибке — один повтор. Если и компактная грамматика окажется велика, клиент повторяет запрос без `format`, передавая схему текстом (`meta.json_mode = "prompt"`).
- Claude: `output_config.format = {"type": "json_schema", "schema": ...}` через `client.beta.messages.create` (SDK `anthropic` 2.x). **Принудительный `tool_choice` (`{"type": "tool"}`) у `claude-sonnet-5-5` и `claude-opus-5-5` возвращает 400**, поэтому от схемы через tool use отказались. Рассуждение адаптивное (у этих моделей его нельзя выключить), глубина — `output_config.effort` (`ANTHROPIC_EFFORT=medium`). Для Sonnet/Opus включён серверный fallback при отказе модели (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`; у Haiku 5.5 его нет);
- OpenAI: Structured Outputs (`json_schema`, `strict`).

Ответ всегда дополнительно валидируется кодом (значения из допустимого набора, мягкое приведение `"true"`/`"N/A"`/`"15"`). При ошибке схемы — **один** повтор с текстом ошибки; валидные критерии первой попытки сохраняются.

**Риск «якоря».** Видя ответ локальной модели, облако может просто соглашаться с ним. Поэтому предусмотрена стратегия `hybrid_strategy`:

| Значение | Как работает | Цена |
|---|---|---|
| `review` (по умолчанию) | Облако видит вердикты локальной модели и подтверждает или исправляет их | 1 облачный вызов |
| `blind` | Облако сначала оценивает **вслепую**; код сравнивает; по расхождениям — один вызов-арбитр, который видит оба обоснования | 1–2 облачных вызова |

Выбор между `review` и `blind` — по замеру на мини-эталоне (раздел 9).

**Модели (переключатель):**

| Провайдер | Модель | Цена, $ за 1 млн токенов (вход / выход) |
|---|---|---|
| Anthropic | `claude-sonnet-5-5` (основная) | 2 / 10 |
| Anthropic | `claude-haiku-5-5` (дешёвая) | 0.10 / 0.50 (промпт до 100K токенов) |
| Anthropic | `claude-opus-5-5` (сильная) | 4 / 20 |
| OpenAI | ID из консоли OpenAI → `OPENAI_MODEL` | **заполнить с официальной страницы цен** |

Цены Claude сверены с platform.claude.com/docs/en/about-claude/pricing 7 ноября 2026. Модели Claude 4.7 и новее используют токенизатор, который даёт примерно на 30% больше токенов, поэтому стоимость считаем **только** по полям `usage` из ответа.

**Кэширование:** системный промпт с чек-листом одинаков для всех диалогов. У Claude помечаем его `cache_control`. Это снижает стоимость и задержку при пакетном прогоне.

### 6.6. Этап 3 — правила финального решения (код)

**Шаг 1. Валидация каждого ответа:**
- значение из допустимого набора критерия (например, `dialogue ∈ {0, 4, 7, 10}`);
- `null` только при `na_allowed = true`;
- все `evidence_turns` в диапазоне `1..N`;
- `quote` найдена в тексте указанной реплики (нормализация регистра и пробелов, нечёткое совпадение ≥ 0.85).

**Шаг 2. Финальный вердикт по критерию:**

| Ситуация | Финальное значение | `agreement` | Уверенность | `needs_review` |
|---|---|---|---|---|
| Облако подтвердило, доказательство проверено | значение | `agree` | high | нет |
| Облако подтвердило, доказательство **не** проверено | значение | `agree` | low | **да** |
| Облако исправило, его доказательство проверено | значение облака | `override` | medium | нет* |
| Облако исправило, доказательство **не** проверено | значение облака | `override` | low | **да** |
| Облако недоступно или ответ невалиден после повтора | значение локальной | `local_only` | low | **да** |
| Локальная модель недоступна (облако становится первичным судьёй) | значение облака | `cloud_only` | ≤ medium | если нет доказательства |
| Обе модели дали невалидный ответ | — | — | — | диалог → `status: "error"` |
| `confidence: low` у облака | значение облака | как есть | low | **да** |
| `blind`: значения совпали / разошлись → арбитр | значение / арбитра | `agree` / `arbiter` | high / medium | если нет доказательства |

Решение «подтвердило/исправило» определяется сравнением значений, а не полем `decision` (модель может ошибиться в поле).

**Статусы доказательства** (`evidence.py`): `verified` — цитата найдена в указанной реплике; `corrected` — цитата найдена в другой реплике, номер добавлен кодом (типичная ошибка ±1 у малых моделей); `no_quote`, `unverified`, `missing` — доказательство не подтверждено. Если номеров нет — подставляется проверенный участок по умолчанию (`default`: первая реплика оператора для `contact`, последняя — для `closure` и т.д.), чтобы `evidence_turns` в `results.json` не был пустым.

\* В аналитике отдельно считаем долю override по каждому критерию: так видно, где слаба локальная модель.

**Шаг 3. Особые правила:**
- **critical:** финальное значение — облака; если **хоть одна** модель или NLP-сигнал указали на нарушение, а финал `false`, ставим `needs_review = true` с пометкой «возможное нарушение»;
- **N/A против «Нет»:** если модели расходятся в этом, ставим `needs_review = true` — это самая частая ошибка;
- **сигнал против вердикта:** NLP-сигнал явно противоречит финалу (например, нашли «меня зовут» в первой реплике, а `contact=false` из-за отсутствия представления) — понижаем уверенность.

**Шаг 4.** Итог считается калькулятором (раздел 5). `needs_review` на баллы не влияет, только на интерфейс и очередь проверки.

### 6.7. Промпты: общие требования

- Системная часть: роль, правила чек-листа (рендер из конфига), правила N/A, требование цитировать.
- Пользовательская часть: метаданные (канал, язык), сигналы, нумерованный транскрипт `[idx] speaker (ts): text`.
- Явно написать: «Если в диалоге нет информации для уверенного вывода, укажи `confidence: low` и объясни, чего не хватает. Не придумывай факты».
- Обоснования писать на **русском** (язык интерфейса), цитаты — на языке оригинала.
- Имя и ID оператора в промпт не передаются (кроме самого текста реплик).
- Каждый шаблон имеет `prompt_version`, который сохраняется в журнале.

### 6.8. Воспроизводимость

- `temperature = 0` у локальной модели и OpenAI (для reasoning-моделей OpenAI, которые её не принимают, — автоматический повтор без неё). **У Claude Sonnet/Opus 5.5 параметр `temperature` удалён из API (400)** — воспроизводимость обеспечивает кэш результатов, а метрика «Воспроизводимость» в `compare.py` показывает фактическую стабильность.
- Ключ кэша: `sha256(реплики диалога + хеш критериев чек-листа + mode + models + strategy + think/effort + prompt_versions)`. Повторный запуск с тем же ключом возвращает сохранённый результат (с пометкой «из кэша», задача считает `from_cache`) или пересчитывает по кнопке «Переоценить» / флагу `--force`. Ошибки и **неполные** оценки (`audit.complete = false`: например, облако упало и итог взят только у локальной модели) не кэшируются — следующий запуск попробует снова.
- **Повторное использование этапа 1.** Если в журнале уже есть валидный ответ локальной модели на тот же диалог с тем же чек-листом, моделью, версией промпта и `think`, он берётся готовым (`stages.local.meta.reused = true`). Поэтому конфигурации 1, 4, 5, 6 из раздела 9.3 гоняют Qwen один раз. `--force` / «Переоценить» отключает и это.
- Журнал на каждую оценку: модели и их версии, версии промптов, версия чек-листа, сырые ответы моделей, токены, стоимость, время каждого этапа.

### 8.2. Обязательные взаимодействия

- Клик по номеру реплики в обосновании прокручивает расшифровку к реплике и подсвечивает её. У звонка дополнительно перематывает плеер на `offset_sec`.
- Пропущенное действие: подсветить проверенный участок (например, первая реплика оператора для `contact`).
- N/A: серый бейдж с причиной; вес критерия показан как «перераспределён».
- Грубое нарушение: заметная красная плашка с цитатой. Итог при этом не обнуляется.
- Плеер для звонков: стандартный `<audio>` с `audio_url` плюс кнопка «Открыть запись в новой вкладке» на случай, если ссылка не проигрывается встроенно.

### 8.3. Совместимость с Dynamics 365

- Без сборщика и фреймворков; относительные пути к файлам.
- Адрес API — только из `config.js` (`window.CQA_CONFIG.apiBaseUrl`), без захардкоженного хоста.
- Все стили под корневым контейнером `.cqa-root`, классы с префиксом `cqa-`, без глобальных стилей `body`.
- Корректная работа внутри `iframe`.
- Входные параметры через query string (`?conversationId=...`); веб-ресурс D365 получает параметры через query-параметр `data`.
- Каждый экран — отдельный модуль `pages/*.js`, который можно отдать как отдельный компонент.

### 8.4. Визуальный стиль

Корпоративный: светлая тема, много воздуха, зелёный акцент в духе бренда Freedom (точный оттенок сверить с их материалами), нейтральные серые, один шрифт без засечек, иконки-контуры. Без мультяшности и игровых элементов. Цвета статусов: зелёный — да, жёлто-оранжевый — частично или низкая уверенность, красный — нет или грубое нарушение, серый — N/A.

## 9. Что проверяем и как сравниваем модели

### 9.1. Мини-эталон

Вручную размечаем **20–30 DEV-диалогов** (≈10 RU, 8 KZ, 7 EN, плюс 2–3 звонка) по чек-листу. Каждую разметку проверяет второй человек. Формат — как `results.json`. Файл `eval/gold/dev_gold.json`.

### 9.2. Выбор локальной модели (первые 2–3 часа)

Прогнать **Qwen3-8B** и **Qwen3.5-9B** в режиме `local` на одних и тех же 10 размеченных диалогах (обязательно с KZ) и сравнить:

| Метрика | Как считать |
|---|---|
| Валидность JSON | Доля ответов, прошедших схему с первого раза |
| Совпадение по критериям | Доля критериев с совпавшим значением |
| Средняя ошибка итога | Средняя абсолютная разница `final_score` с эталоном |
| Время на диалог | Секунды, среднее и максимум |
| Память | Влезает ли в железо вместе с остальным |
| Качество на KZ | Те же метрики только по KZ-диалогам |

Берём ту, что лучше по точности при приемлемом времени. Если на KZ обе слабы — в локальном этапе переводить KZ-реплики на RU той же моделью или помечать KZ-диалоги низкой уверенностью, чтобы облако проверяло их тщательнее.

### 9.3. Сравнение Claude и OpenAI поверх локальной модели

Прогнать на полном мини-эталоне шесть конфигураций:

| # | Конфигурация |
|---|---|
| 1 | `local` (выбранная Qwen) |
| 2 | `cloud` + Claude |
| 3 | `cloud` + OpenAI |
| 4 | `hybrid` + Claude (`review`) |
| 5 | `hybrid` + OpenAI (`review`) |
| 6 | Лучший из 4–5 в стратегии `blind` |

**Метрики (`eval/compare.py` выводит таблицу):**

| Метрика | Зачем |
|---|---|
| Совпадение по каждому критерию | Где слабые места |
| Точность определения N/A | Самая частая ошибка (N/A против «Нет») |
| Средняя абсолютная ошибка итога | Близость к эталону в целом |
| Precision / recall по `critical` | Комплаенс: пропуск нарушения хуже ложной тревоги |
| Доля override облаком | Насколько облако реально меняет оценки |
| **Полезные override** | Из исправлений облака — доля, которые приблизили к эталону |
| **Вредные override** | Доля, которые испортили верный ответ локальной модели |
| Доля `needs_review` | Нагрузка на людей |
| Стоимость одной оценки, $ | По `usage` всех вызовов |
| Время одной оценки | Укладываемся ли в час на prod |
| Воспроизводимость | Два прогона подряд: доля полностью совпавших результатов |

**Решение:** провайдер по умолчанию — тот, у кого лучше точность при приемлемой стоимости. Таблица сравнения — готовый слайд для защиты («мы измерили, а не угадали»).

### 9.4. Приёмка по требованиям гайда

| # | Требование | Проверка |
|---|---|---|
| 01 | Создать / изменить чек-лист: критерии, формулировки, вес, тип, N/A, шкала; сохранить конфигурацию | Добавить новый критерий через интерфейс → он появляется в оценке без правки кода |
| 02 | Загрузить транскрипт, выбрать чек-лист, оценить; RU / KZ / EN; бот и система как контекст | Прогон по одному диалогу каждого языка и канала |
| 03 | Ответ, баллы, вес, объяснение, реплика-доказательство; проверенный участок при пропуске; причина N/A; итог и секции | Визуальная проверка карточки на 5 разных диалогах |
| — | Пересчёт шкал с весом, перераспределение при N/A, отдельный флаг грубой ошибки, округление | Тесты калькулятора проходят |
| 04 | Из списка в карточку; ссылка ведёт к сообщению или фрагменту звонка; плеер | Клик по каждой ссылке |
| 05 | Апелляция: критерий + комментарий; проверяющий видит оценку, комментарий, фрагмент | Сценарий целиком |
| 06 | Решение с причиной, пересчёт итога, в карточке исходная оценка, решение и финал | Итог меняется корректно |
| — | Новые диалоги реально анализируются | Загрузка незнакомого JSON → оценка с журналом вызовов |

### 9.5. Проверки `results.json` перед push (`validator.py`)

- UTF-8, валидный JSON, без комментариев и лишних запятых.
- `schema_version = "1.0"`, есть `team_name`, `model.mode` (`hybrid`), `model.name` перечисляет все модели (например, `"Qwen3-8B (local) + claude-sonnet-5-5"`).
- Одна запись на диалог, без пропусков и дубликатов; ID совпадают с API.
- В prod **ровно 10** записей, включая ошибки.
- `status = "ok"`: все 8 критериев ровно по одному разу, значения из допустимого набора.
- `status = "error"`: `criteria = []`, `score = null`, заполнен `error`.
- `evidence_turns` — номера по исходному массиву, от 1.
- `final_score` от 0 до 100, два знака; `critical_flag` равен `value` критерия `critical`.

**Открытый вопрос к организаторам:** если на контрольной проверке критерий заменён, какой чек-лист использовать для `results/prod/results.json` — исходный (8 фиксированных кодов) или новый? По умолчанию экспортируем **исходные 8 кодов**: приложение запрещает менять коды критериев.

### 9.6. Юнит- и интеграционные тесты

- Калькулятор (раздел 5).
- Адаптеры: метки времени сохраняются как есть; `idx` совпадает с позицией в исходном массиве.
- `evidence.py`: правильная цитата проходит, выдуманная — нет; номер вне диапазона ловится.
- `decision.py`: каждая строка таблицы из 6.6.
- Конвейер целиком с mock-моделями (без сети).
- Экспорт и валидатор на фиктивном наборе, включая запись с ошибкой.

## 10. Прогон контрольного набора (за час до стоп-кода)

Одна команда в **локальном терминале** (в папке репозитория):

```bash
export PYTHONPATH=backend          # PowerShell: $env:PYTHONPATH="backend"
python -m app.cli run --group-id <PROD_ID> --dataset PROD \
  --mode hybrid --provider anthropic --local-model qwen3-8b \
  --out results/prod/results.json --expect 10
python -m app.cli validate results/prod/results.json --expect 10
git add results/prod/results.json && git commit -m "prod results" && git push
```

Относительные пути CLI считаются от корня репозитория. `run` сам валидирует файл после записи и возвращает код 1 при ошибках. Если API организаторов недоступен, используется последняя копия из `data/raw/`.

- Облачные вызовы по диалогам идут параллельно (ограничение 3–5 одновременно).
- Если облако упало — результат локальной модели с `needs_review`. Если упало всё — `status: "error"`, запись не пропадает.
- **Заранее отрепетировать** на DEV с замером времени. Цель — 10 диалогов меньше чем за 15 минут.

Режим, провайдер, локальная модель, стратегия и чек-лист по умолчанию меняются из интерфейса («Настройки модели») и хранятся в БД; `.env` задаёт значения по умолчанию.

### 11.2. Docker Compose

- `backend`: FastAPI, раздаёт `frontend/` как static, том для SQLite.
- Локальная модель:
  - **Linux + NVIDIA:** отдельный сервис `ollama` или `vllm` в compose с пробросом GPU;
  - **macOS:** Docker не даёт контейнерам доступ к GPU Mac. Поэтому Ollama запускается **нативно на ноутбуке**, а backend обращается к ней по `http://host.docker.internal:11434`.

**Шаги (все команды — в локальном терминале ноутбука, в папке репозитория):**

1. `cp .env.example .env` и заполнить ключи.
2. (macOS) в **отдельной вкладке локального терминала**: `ollama serve`, затем в той же или новой вкладке `ollama pull qwen3:8b`.
3. Вернуться во вкладку с репозиторием: `docker compose up --build`.
4. Открыть `http://localhost:8000`.
5. В разделе «Диалоги» загрузить набор по `group_id`.

## 14. Трактовки правил, принятые командой (меняются через редактор чек-листа)

Эти трактовки записаны в поле `guidance` критериев `default_checklist.json` и попадают в промпт. Если жюри или организаторы трактуют иначе — правим текст в разделе «Чек-листы» и сохраняем новую версию, код не меняется.

| Критерий | Трактовка |
|---|---|
| `identification` | Если оператор не раскрывал данные счёта и не выполнял защищённых действий (например, клиент отказался от проверки и получил только общую инструкцию) — N/A. Фраза «вижу у вас на счёте…» без подтверждения личности — «Нет». |
| `critical` | Раскрытие сведений о счёте **самому клиенту** без идентификации оценивается в `identification`, а не как грубая ошибка. Грубая ошибка — данные других клиентов, пароли и коды, служебные сведения. |
| `discovery` | Уточнять было нечего и оператор сразу ответил по существу — N/A, а не «Да». |
| `closure` | Нужны оба условия: (итог или предложение помощи) **и** прощание. Только «Хорошего вечера!» без итога — «Нет». |
| `contact` | «[Имя скрыто]» в звонках = оператор представился (имя скрыто анонимизацией). |

**Открытые вопросы к организаторам:** (1) какой чек-лист использовать для `results/prod/results.json`, если критерий заменён (по умолчанию — исходные 8 кодов, см. 9.5); (2) считается ли «Хорошего вечера!» без предложения помощи завершением.
